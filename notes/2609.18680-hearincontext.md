# HearInContext：论文阅读笔记

- **论文**：HearInContext: A Benchmark for Implicit Context in Speech Recognition
- **作者**：Yifan Gao, Yao Tian, Hongbin Suo（OPPO AI Center，北京）
- **出处**：arXiv 2609.18680。v1 提交于 2026-09-16，v2 更新于 2026-09-21。本笔记基于 v1。
- **状态**：预印本，**未经同行评审**，没有找到收录记录（见第 8 节）。
- **代码**：https://github.com/OPPO-Mente-Lab/HearInContext （Apache-2.0）
- **数据**：https://huggingface.co/datasets/OPPOer/HearInContext
- **一句话**：做了一个中英双语 benchmark，测试 ASR 能不能从**没有提到目标词**的对话上下文（隐式上下文）里判断同音词该写成哪个。同一段音频配四种上下文做对比。然后微调 Qwen3-ASR-1.7B，隐式召回提升约 11 个点，通用 ASR 基本没有退化。

---

## 1. 要解决的问题

同音词光听声音分辨不出来，要靠语义。比如英文 flour / flower：前面在聊烘焙就是 flour，在聊送花就是 flower。

已有的 contextual ASR 工作和 benchmark 大多给的是**显式**提示：热词表、实体列表、幻灯片、领域描述。这些提示里**往往直接出现了目标词**。所以识别变好时说不清原因：

1. 模型真的理解了上下文的**语义**？
2. 还是只是在上下文里**看到了这个词**，照着抄？

另外，如果不同条件用的是不同的录音，录音质量差异本身也会影响结果。

作者的思路：**音频固定，只换上下文**，并且在隐式上下文里**排除所有候选词**。

## 2. Benchmark 设计（第 2 节）

### 2.1 四种条件（核心）

同一段音频、同一个参考文本，配四种上下文。括号里是代码仓库中的条件代号：

| 条件 | 上下文内容 | 测什么 |
|---|---|---|
| No context（C0） | 无 | 纯靠声音，歧义无法解决时的底线 |
| **Implicit（C1）** | 支持目标语义，但**不出现任何候选词** | 能不能靠语义推断 |
| Explicit（C3） | 在某一轮回复里**直接写出目标词** | 给了词能不能用上（上限参考） |
| Unrelated（U） | 其他领域、其他组的无关对话 | 无关上下文会不会干扰 |

四组对比分别回答：上下文有没有用（Implicit vs No）、直接给词还能多拿多少（Explicit vs Implicit）、无关历史有没有伤害（Unrelated vs No）。

消融实验另有 `USER_ONLY` 和 `FULL_HISTORY` 两个条件（见 4.3）。

### 2.2 为什么用"助手回复"做上下文

默认上下文是**助手（系统）的历史回复**，不是用户之前说的话。原因：

- 系统生成的文本本来就是准确的，**没有 ASR 错误**；用户之前的话需要先识别，本身可能有错。
- 助手可以确立话题、建议下一步，但不会替用户说出他接下来要用的词。

### 2.3 数据构造

- **候选组**：一组同音词，能填进同一个句子框架（例：I need some ___ for ...）。每组只**合成一段锚点音频**，在不同语义分支之间复用。
- **对话**：为每种解释写一段支持它的助手历史，再派生出 explicit 和 unrelated 版本。
- **自动检查**：参考文本中目标词恰好出现一次；implicit 和 unrelated 不出现任何候选；explicit 只出现目标候选。英文组还用 DeepSeek-V4-flash 检查发音与词义是否对应、句子是否自然、上下文是否真的支持该解释。
- **语音合成**：CosyVoice2-0.5B。说话人参考音频：中文来自 AISHELL-3，英文来自 VCTK。训练用 96 个说话人，测试用另外 26 个（不重叠，男女各半）。每个测试组用一男一女各合成一遍，16 kHz。

### 2.4 规模（表 1）

| 划分 | 语言 | cases | 音频数 | 小时 |
|---|---|---|---|---|
| Train | ZH / EN | 5,400 / 1,800 | 10,800 / 3,600 | 17.25 / 4.20 |
| Dev | ZH / EN | 600 / 200 | 1,200 / 400 | 1.92 / 0.48 |
| Test | ZH / EN | 2,656 / 1,108 | 2,618 / 1,100 | 2.37 / 0.81 |

- 测试集：1,859 组，3,764 个 case，3,718 段音频，每个条件 7,528 个 case×voice 样本。
- 平均每组约 2 个 case，所以大多数是**二选一**的同音词对。
- 训练/开发集是另一套：**每个目标句单独合成**（不共享音频），上下文由 DeepSeek-V4-flash 生成并审核，和测试集的目标词**没有重叠**。

## 3. 实验设置（第 3 节）

### 3.1 模型

- **无上下文基线**：FireRedASR2-AED、SenseVoice-Small、Whisper-Large-v3。
- **支持上下文的模型**：Qwen3-ASR-0.6B / 1.7B、VibeVoice-ASR-7B、Seed-ASR（通过 Seed-ASR 2.0 API 调用）。
- 各模型用自己原生的上下文接口；Qwen 直接拿到历史文本，不另加指令。vLLM + 贪心解码。

### 3.2 微调（Qwen3-ASR-1.7B，全参数）

- 训练数据按条件配比（详见 5.1）：80/20/0、80/10/10、80/0/20。
- **Explicit 只用于评测，不参与训练**，因此可以用来测迁移。
- 每种配比 14,400 条，中英等量。AdamW，lr 1e-5，2% warmup + 线性衰减，batch 16，900 步，每 100 步存一个 checkpoint。
- checkpoint 按开发集上的一套排名公式选（错误率、召回率排名求和，再加 0.25 × 跨说话人标准差的排名），最终分别选中第 700、800、400 步。

### 3.3 指标

- 中文 CER、英文 WER；**目标召回率 R**（详见 5.2）。
- 通用能力：AISHELL-1、LibriSpeech clean/other（无上下文）。
- 上下文迁移：ContextASR-Speech（粗粒度领域上下文下的实体召回）。
- 真实录音热词：Test-AISHELL1-NE（808 条，统一给 400 个热词）。

## 4. 结果（第 4 节）

### 4.1 隐式 vs 显式（表 2）

Qwen3-ASR-1.7B：

| | No context R | Implicit R | Explicit R |
|---|---|---|---|
| 中文 | 46.20 | 69.92 | 82.79 |
| 英文 | 43.95 | 73.56 | 90.61 |

- No context 的 R 都在 40–46% 左右，这是设计决定的（见 5.2），可以当作 sanity check。
- 四个支持上下文的模型都能从隐式上下文中获益（R 提升 20–30 个点）。
- 但**显式提示还能再多拿 13–17 个点**。结论："直接告诉它是哪个词"和"让它从语义里推断"是两种不同的能力，后者明显更难。
- 模型之间：VibeVoice 显式召回最高，Qwen-1.7B 隐式召回最高；VibeVoice 中文隐式 CER 却比 Qwen 低。说明 CER 和 R 衡量的是不同的东西，要一起看。
- Seed-ASR 英文显式 R 只有 73.92，明显偏低（可能和 API 的上下文接口有关，文中没有解释）。

### 4.2 微调：收益和鲁棒性的权衡（表 3）

逐区块的解读见 5.3。核心结论：

1. **所有配比都显著提升隐式召回**。摘要里的"+11.0 / +11.5"对应的是 80/10/10（80.91−69.92、85.02−73.56），**不是**召回最高的 80/20/0（+14.6 / +14.5）。
2. **80/20/0 的坑**：在无关上下文下 R 反而掉 4.6 个点。**空上下文样本不能替代无关上下文样本。**
3. **没有哪个配比在所有条件下都最好。**
4. **是真的学会用上下文了吗？** No context 的 R 几乎没变，Implicit 的 R 大幅上升，"Implicit − No context" 的差距扩大了 10.94 / 11.28 个点。
5. **迁移**：没有训练过的 Explicit 条件也提升了（中文 82.79→90.66，英文 90.61→96.62）；真实录音的热词任务也有提升。
6. **通用 ASR 没有退化**：变化都在 0.1 个百分点以内。

### 4.3 上下文来源消融（表 4）

结论：只用助手回复，基本等于用完整历史。详细解读见 5.4。

## 5. 问答整理

### 5.1 80/20/0、80/10/10 这些数字是什么意思？

是**训练数据里三种上下文样本各占的百分比**，顺序固定为 **隐式 / 空上下文 / 无关上下文**，三个数加起来是 100。

每条训练样本由三部分组成：一段音频、这段音频的正确文本、一段对话历史。三个数字的区别只在于对话历史是哪一种：

| 位置 | 上下文类型 | 样本长什么样（以 flour 为例） | 模型从中学到什么 |
|---|---|---|---|
| 第 1 个数 | Implicit 隐式 | 助手在聊烤蛋糕，但没出现 flour / flower → 答案 flour | 根据语义选对同音词 |
| 第 2 个数 | No context 空 | 没有任何历史 → 答案 flour | 没上下文时照常靠声音 |
| 第 3 个数 | Unrelated 无关 | 助手在聊航班改签 → 答案 flour | 上下文不相关就忽略，不被带偏 |

每种配比总共 14,400 条（代码仓库中的文件名如 `train_mixtures/m80_10_10.jsonl`）：

| 配比 | 隐式 | 空上下文 | 无关上下文 |
|---|---|---|---|
| 80/20/0 | 11,520 | 2,880 | 0 |
| 80/10/10 | 11,520 | 1,440 | 1,440 |
| 80/0/20 | 11,520 | 0 | 2,880 |

隐式固定 80%，只变动剩下 20% 在"空"和"无关"之间怎么分。

分法不同，结果为什么不同：

- **80/20/0**：模型见过的上下文要么有用、要么没有，**从来没见过"有上下文但没用"**，于是学成了"只要有上下文就信"。隐式召回最高（中文 84.5），但给无关上下文时召回从 44.1 掉到 39.4。
- **80/10/10**：见过无关上下文，学会了"不相关就忽略"。隐式召回稍低（80.9），无关条件下几乎不掉（43.9）。
- **80/0/20**：最不容易被干扰（44.9，略高于 Base），但中文隐式召回最低（79.2）。

**"空上下文"和"无关上下文"对模型来说是两种不同的训练信号**，前者替代不了后者。

### 5.2 No context CER 和 No context R 是什么意思？

拆开看：**"No context"是测试条件**（不给任何对话历史，只给音频），**CER 和 R 是指标**。表里的 Implicit CER、Unrelated R 也是同样的结构。

**CER（字错误率）**：衡量整句转写错了多少，越低越好。中文按字算，英文用 WER 按词算。

> CER = (替换 + 删除 + 插入的字数) ÷ 参考文本总字数

**R（目标召回率）**：只看目标词出没出现在输出里，越高越好。每个样本最多算一次命中。

例子（自编）：参考文本"这篇文章讨论了公民的**权利**"，共 12 个字；模型输出"……公民的**权力**"。CER = 1/12 ≈ 8.3%；R = 0（目标词没出现）。

**为什么两个都要看**：同音词错了在整句里只是一两个字，CER 只涨一点，容易被掩盖。本文关心的恰恰是那个词选对没有，所以 **R 是主要指标**，CER 用来看整句质量有没有变差。

注意：代码文档说明，R 衡量的是"出现"。如果输出里目标词和竞争词**同时出现**，也算命中。所以它不是严格的"二选一准确率"，多余的输出由 CER 来反映。

**No context R 为什么只有约 45%**：测试集里同一组同音词**共用同一段音频**。不给上下文时，模型对这段音频只能输出一种写法：写 flour，flour 分支对、flower 分支错；写 flower 则反过来。所以二选一的组里 **R 的上限约 50%**，这是设计故意造成的"只能靠猜"的基线。论文原话："One audio-only transcription cannot match every branch reference"。同理，No context CER（中文 7.38）也被这个机制人为抬高了，不能和 AISHELL-1 上 1.5% 的 CER 直接比。

回到表 3：No context R 几乎不变（46.20 → 46.25）说明模型没有"更会猜"；Implicit R 大涨（69.92 → 80.91）说明给了上下文后选对更多。两者合起来就是作者的核心论证：**提升来自对上下文的利用。**

### 5.3 表 3 怎么读？

表 3 对比的是**同一个模型的 4 个版本**（列）：Base（未微调）和三种配比微调后的模型。行分成 5 个区块，每块回答一个问题：

| 区块 | 测什么 | 要回答的问题 |
|---|---|---|
| ① HearInContext 中文 | 本文 benchmark，三种上下文条件下的 CER 和 R | 学会用隐式上下文了吗？会被无关上下文带偏吗？ |
| ② HearInContext 英文 | 同上 | 同上 |
| ③ General ASR | AISHELL-1、LibriSpeech clean/other，**不给上下文**，真实录音 | 通用识别能力有没有变差（灾难性遗忘）？ |
| ④ ContextASR 实体召回 | 另一个 benchmark，只给粗粒度的领域上下文，看实体认对多少 | 能力能否迁移到**另一种形式**的上下文？ |
| ⑤ AISHELL-1-NE | **真实录音**，808 句含命名实体，有/无 400 词热词表 | 在真实语音、显式热词场景有没有收益？ |

区块 ①② 的主要数字：

| 指标（ZH / EN） | Base | 80/20/0 | 80/10/10 | 80/0/20 |
|---|---|---|---|---|
| Implicit R | 69.92 / 73.56 | **84.53 / 88.04** | 80.91 / 85.02 | 79.20 / 85.24 |
| Unrelated R | 44.05 / 41.34 | 39.44 / 36.78 ↓ | 43.92 / 41.25 | **44.94 / 42.46** |
| No context R | 46.20 / 43.95 | 46.31 / 44.27 | 46.25 / 44.13 | 46.22 / 43.59 |

另一个细节：即使是 Base，Unrelated 下中文 CER（8.48）也**比 No context（7.38）高**，说明无关上下文本身就有伤害，不是微调后才出现。

**4.2 节末尾那段话逐句解读**

> For 80/10/10, AISHELL-1 and LibriSpeech error rates remain within 0.1 percentage points of Base.

| | Base | 80/10/10 | 变化 |
|---|---|---|---|
| AISHELL-1 CER | 1.51 | 1.50 | −0.01 |
| Libri clean WER | 1.63 | 1.68 | +0.05 |
| Libri other WER | 3.40 | 3.33 | −0.07 |

有升有降，幅度都很小，结论是**没有灾难性遗忘**。在一万多条 TTS 数据上做全参数微调，这并不是理所当然的。注意"百分点"是绝对差值：1.63 到 1.68 换算成相对变化约 +3%。

> ContextASR-Speech coarse recall improves by 0.60/0.69 points (ZH/EN).

80/10/10 的实体召回：中文 89.00→89.60，英文 85.77→86.46。**但这句只报告了 80/10/10**，另外两个配比在英文上是下降的：

| ContextASR 英文 | Base | 80/20/0 | 80/10/10 | 80/0/20 |
|---|---|---|---|---|
| 实体召回 | 85.77 | 84.66（−1.11） | 86.46（+0.69） | 83.85（−1.92） |

所以这项迁移不稳定，论文的表述有挑选之嫌。只训练了一次，±1 个点也可能是噪声。

> All mixtures also improve hotword-conditioned recognition on Test-AISHELL1-NE real recordings: 80/10/10 gives the lowest CER, and 80/20/0 the highest recall.

| 给热词时 | Base | 80/20/0 | 80/10/10 | 80/0/20 |
|---|---|---|---|---|
| CER ↓ | 3.80 | 3.52 | **3.51** | 3.69 |
| 实体召回 R ↑ | 73.09 | **75.85** | 74.15 | 74.68 |

这是**全文唯一一个真实录音上的上下文实验**，可以部分缓解"训练和测试都是 TTS"的担心。但要注意：

- 热词表是**显式**提示。这里证明的是"隐式数据训练 → 迁移到真实语音的显式热词"，**不是**"隐式上下文在真实语音上有效"。
- 不给热词那一行几乎没变（80/10/10 R 67.37 vs Base 67.48），提升来自**更会用热词**，而不是真实语音识别变好了。

一句话：80/10/10 学会了用上下文，同时没有损害通用识别，收益还能迁移。但要打折扣：ContextASR 迁移只有这一个配比成立；真实录音测的是显式热词；差异普遍只有零点几个百分点，且只训练了一次。

### 5.4 表 4 怎么读？

表 4 回答的是：**上下文用对话里的哪一部分最好？** 固定 Base 模型、Implicit 条件、同一批音频，只换上下文来源：

| 上下文来源 | 中文 CER ↓ | 中文 R ↑ | 英文 WER ↓ | 英文 R ↑ |
|---|---|---|---|---|
| Assistant-only（默认） | 4.67 | 69.92 | **5.15** | **73.56** |
| User-only（人工标注的准确文本） | **4.45** | 67.85 | 5.71 | 70.67 |
| Full-history | 4.69 | **70.44** | 5.54 | **73.56** |

作为参照，不给上下文时中文 R 约 46、英文约 44。三种来源都带来 20 多个点的提升，彼此之间只差几个点。

1. **只用助手回复，基本等于完整历史**。中文 CER 几乎一样、R 只低约 0.5；英文 R 相同、WER 反而更低。
2. **历史越多不一定越好**。英文完整历史的 WER 比只用助手回复还高，可能是更长的上下文带来更多干扰（论文没有分析原因）。
3. **只用用户的话最差，而且 CER 和 R 结论不一致**。中文 CER 最低但 R 也最低；英文两项都最差。

作者的结论："assistant replies retain most full-history benefit without requiring transcriptions of prior user speech"。实际系统中，用户之前的话只能来自 ASR 输出，可能恰恰错在同音词上；助手回复是系统自己生成的，一定准确，也不需要额外计算。而且表里的 User-only 用的是理想条件下的准确文本，**所以这个比较对助手回复是偏保守的**。

打折扣的地方：

- **存在一定的循环论证**：benchmark 从构造时就让助手回复去"支持目标语义"。在这样的数据上发现"助手回复信息量够"，不能直接推广到真实对话，真实对话里关键信息完全可能只在用户自己的话里。
- 只测了 Base 模型，没测微调后的模型。
- 三种来源的文本长度不同但没有报告，分不清差异来自信息来源还是信息量。
- 差距只有零点几到两三个点，只跑了一次。

## 6. 容易误读的地方

- **摘要里的 11 个点是 80/10/10**，不是最好的那个配比。
- **测试音频全部是 TTS 合成的**。唯一的真实录音实验（AISHELL-1-NE）是**显式热词任务**，不是隐式上下文。
- **No context 下 R ≈ 45% 不是模型差**，而是共享音频的设计让它只能猜（5.2）。
- **R 衡量的是"出现"**，不是严格的二选一准确率（5.2）。
- **ContextASR 的迁移只有 80/10/10 成立**，另两个配比英文是下降的（5.3）。
- **v2 可能改过 Explicit 条件**。代码文档提到"Revised C3 changes the context input"，还把 C3 按显式提示在历史中的位置（depth 0/2/4）分组。所以 v1 和 v2 的 Explicit 数字可能不一样，引用前要核对版本。

## 7. 批判性评价

**优点**

- 实验设计很干净：**同一段音频** + **候选词排除** + 四个对照条件，把"语义推断"和"抄写上下文里的词"分开了。这是本文最大的贡献。
- "Implicit − No context 差距"这个论证简单有效。
- "空上下文不能替代无关上下文"对任何做上下文 ASR 训练的人都有直接参考价值。
- 代码、数据、训练配比都开源，还提供了配对 bootstrap 置信区间工具（论文正文里却没有报告置信区间）。

**不足和疑问**

1. **训练和测试用同一个 TTS**（CosyVoice2），一部分提升可能来自适应 TTS 音频。No context CER 变化很小，这个担心不算大，但仍需在真实语音上验证。
2. **上下文都由 LLM 生成**，模型可能学到了 LLM 对话的风格，换到真实助手的回复上效果可能打折。
3. **只有一次训练、没有方差或显著性检验**，0.1 个点级别的差异不宜过度解读。checkpoint 选择公式较复杂，像是事后设计的。
4. **任务形式比较简单**：大多是二选一同音词，句子框架固定。真实场景还有近音词、多个歧义点、长上下文、话题切换。
5. 只微调了 Qwen 一个模型；不公开微调后的权重。
6. 缺少失败案例分析。

**为什么关注这个问题**（推断，作者没有明说）：

1. **手机语音助手就是这个场景**。OPPO 的语音助手"小布"已接入大模型做多轮对话。用户常常承接助手刚说的内容，而助手回复是产品里现成的、准确的文本。
2. **中文同音词问题尤其严重**，论文也以中文为主。
3. **大模型 ASR 让这件事变得可行**。Qwen3-ASR、Seed-ASR 都能直接接收文本上下文，问题变成了"模型到底用没用对"，所以先做评测再做微调。
4. **工业部署关心鲁棒性**，所以大量篇幅花在"无关上下文会不会伤害"和"通用 ASR 会不会退化"上。

## 9. 数据集与代码

- **代码**（GitHub，约 1.5 MB）：评测脚本（CER/WER、目标召回、按条件和说话人拆分）、配对 bootstrap 置信区间、Qwen3-ASR 微调和解码入口、AISHELL-1-NE 实体评测。评测只需 CPU，训练和解码需要 GPU。**不提供微调后的权重。**
- **数据**（Hugging Face `OPPOer/HearInContext`）：训练集和测试集，数据卡里说明了构造方法、语音合成、参考说话人和数据许可。
- **测试集格式**（JSONL，每行一个样本）：

```json
{"example_id":"demo::C1::voice1","language":"en","condition":"C1",
 "reference_text":"Please check the flour.","branch_word":"flour",
 "parent_id":"demo","case_id":"demo_a","speaker":"voice1"}
```

  - `condition`：`C0` 无上下文、`C1` 隐式、`U` 无关、`C3` 显式、`USER_ONLY`、`FULL_HISTORY`。
  - `parent_id` 是同音词组，`case_id` 是其中一个语义分支，`speaker` 是两个合成声音之一。
  - `C3` 样本额外带 `explicit_cue_depth`（0 / 2 / 4），表示显式提示在历史中的位置。
- **评测命令**：

```bash
python evaluation/evaluate.py --manifest test.jsonl \
  --hypotheses predictions.jsonl --output outputs/metrics.json
```

## 10. 和已读论文的联系 / 对产品的启发

- 和 *The Gift of Feedback*（2310.00141）互补：那篇是从**用户修改**里学新词（离线、长期），这篇是用**当前对话语境**在识别时就选对词（在线、即时）。
- 对听写类产品（类 Wispr Flow）：
  - 可用的隐式上下文很多：当前 App、输入框前文、正在回复的消息、邮件主题。这些对应本文的"助手回复"：**系统侧已有、准确、免费**。先用好它们，比把用户之前的听写结果全塞进上下文更划算、更稳（表 4）。
  - 训练模型使用上下文时，**一定要混入无关上下文样本**（参考 80/10/10），否则用户一换话题模型就会被旧上下文带偏。
  - 评测时借鉴本文做法：同一段音频配有关、无关、空三种上下文，单独统计**目标词召回**，不只看 CER/WER。
